# 调查黑板：调查-进化建议书-天气卡方案策划-20261029（进化师）
> 源头任务：对话「@图1 天气展示页面能否优化一下界面给我方案策划」；本板为进化师独立取证，聚焦策划案的事实精度与可落地性。开工前查索引：调查黑板无「天气界面」主题板，新建。

【结论】1【高】策划案落点表文件错位：策划称弹卡"结构"在 public/js/dom-topbar.js，但天气数据逻辑（fetch/渲染/建议文案 zf3dCwSetDesc）实际在 public/js/app-zf3d.js L716-746（zf3dCwLoadWeather），dom-topbar.js 仅 18 行且只含弹卡初始 HTML 骨架；方案A若只改 dom-topbar+css 而不动 app-zf3d.js 的赋值逻辑（el.textContent 拼接 L730），层级重排会与 JS 写入方式冲突。（证据：read_lines app-zf3d.js L700-760；dom-topbar.js 全文 18 行）

【结论】2【中】方案C"今明预报需天气接口支持高低温"前提可零成本满足：open-meteo 同一接口只需 URL 追加 &daily=temperature_2m_max,temperature_2m_min（含 &forecast_days=2），fetch 一次请求即可带回，无需换接口或新增请求；湿度 humidity_2m 同样可加进 current 参数。（证据：app-zf3d.js L720-721 现有 URL 仅 'current=temperature_2m,weather_code'；search_in_files "temperature_2m" 全 public/js 仅 2 处命中）

【结论】3【中】"建议文案"（如'阳光正好，适合出门走走'）生成链路未在策划案改动清单中定位：L734 只传 pair[1] 天气名给 zf3dCwSetDesc，建议语属硬编码映射，重排该行需同步定位此映射表，否则会出现新旧两套建议语并存。（证据：app-zf3d.js L734；策划案落点表未提及）
