# 策划案：对话树巡检大师 —— 每日逐对话分析+修复回笼机制
> 版本：v2.2（v2.1 合入第1轮收口 9 条裁决；本轮合入第2轮收口 5 条 P2 验收钉子，见「八、第2轮收口裁决」）
> 日期：2026-10-29
> 实查依据：server/db.py（sessions/chat_history/chat_history_archive 存储实查，841-850 行迁移逻辑）；父子关系仅存在于前端 DOM 6 类 SrcId（agent-01-project-memory.js:2021，含施工队 _raceSrcId）；roles_db.json 角色链 策划5→施工6→反驳6.5→进化6.75→审核7→验证7.5→总结11；score_parser.py【自评】2026-10-17 已停用，对话级评分空缺；车道闸门并发安全值 8（2026-10-29 实测 429 上限 8~10）。

## 一、定位与边界
巡检大师（建议 order=6.9，进化师分支）每天自动遍历全部对话树（主对话+孩子窗），逐个分析打分，产出《巡检日报》与《问题清单》，并驱动修复闭环。**只读+建议权限，禁止直接改对话/代码**（防 chat_manage 误关 cb337 类事故重演）；修复动作走现成通道（回笼/课题池），人工拍板。

## 二、任务计划（四阶段，串行依赖）
- **P1 对话树持久化（前置，~1天）**：sessions 表加 parent_session_id；6 类派窗链路（summarizer/qc/thinker/custom/expert/race）后端同步写入。依赖：无。是 P2~P4 的前提。
- **P2 巡检大师角色（~0.5天）**：roles_db 注册角色+分析 prompt。依赖 P1（可先盲扫跑通）。
- **P3 日跑调度（~1天）**：schedule 定时+车道闸门限并发 8，深夜批跑。依赖 P2。
- **P4 修复闭环（~1天）**：问题清单→回笼重做（复用回笼策划案机制）→同根因复现≥3 入进化师课题池（现成机制）。依赖 P3。
- 总量 3.5 天，可按 P2（盲扫版）→P1→P3→P4 交付，最快半天出最小闭环。

## 三、实现方法
1. **P1**：db.py 迁移加列（参考 841-850 行既有迁移写法）；派窗时后端随派窗 API 显式传 parent_session_id（前端 SrcId 是 DOM 属性，后端拿不到，勿猜）。坑：兼容 parent 为 NULL 的存量对话；改后必须实测 6 类派窗各开一次。
2. **P2 每对话固定四问**：①目标是什么（取首问）②实际完成了什么（查 git diff/文件产出等实证，不听自报）③完成度打分 0-100（证据锚定）④失败归因五选一：策划错/施工假完成/审核放水/上下文断裂/工具障碍。产出 per-对话一行 → daily_inspection.jsonl →《巡检日报》。
3. **P3 分级成本控制**：全量跑轻量摘要级（首问+最终答复+git 状态，约 1~2k token/个），仅低分或自报与证据矛盾时升级深分析（读全 chat_history）。200 个/天 ≈ 0.5~1M token/天。过车道闸门并发≤8，放深夜。
4. **P4 闭环**：可修复项→生成回笼素材包（复用回笼策划案的 fan()/素材包机制）；复现≥3→课题池（check_topics.py 巡检脚本已有雏形）。验收硬指标：**跑一天后日报必须指出 ≥1 个真实未完成任务且与人工判断一致**，否则机制不算生效。

## 四、愿景
最终形态：每天早上工作台自动多一份《巡检日报》——昨日 200 个对话逐一评分排名、假完成清单、根因分布；点任一条可直接"回笼重做"或"入课题池"。系统从"事后救火"变"每日体检"，假完成率逐日下降可量化（self_scores.jsonl + daily_inspection.jsonl 趋势）；进化师课题池由巡检自动供弹，进化路径十阶段中"验收不知道好不好"与"自循环长期评分"两阶段被同时补上。远期：日报自动生成提示词优化建议、评分趋势接入能力进化树驱动新能力节点。

## 五、风险与备选
- 风险1：巡检大师权限过大误伤生产 → 只读+建议，写权限零授予；备选：降级为"仅出日报，人工点回笼"。
- 风险2：P1 动核心存储/派窗链路 → 迁移用加列不改旧列；每步 git 快照可回滚；实测 6 类派窗。备选：sidecar 表 session_tree.jsonl（零改主表）。
- 风险3：日 200 个成本失控 → 分级分析兜底；备选：先日跑 50 试点一周再全量。
- 风险4：与审核员/验证师职能重叠 → 层次互补：审核/验证管"当时"，巡检管"关窗后的跨对话追责与复盘"。

## 六、反驳项
- 反1：质疑"AI 分析 AI 的对话，评分会不会全是客套高分（重蹈自评覆辙）？" → 应对：评分强制证据锚定（git diff/文件存在/退出码），无证据项按 0 分计；日报与人工抽检对齐率作为生效验收标准。
- 反2：质疑"P1 动核心存储，代价大于收益" → 应对：最小化为一张加列+6 处传参；实测风险大则改用 sidecar session_tree.jsonl 零改主表。
- 反3：质疑"200 个/天是拍脑袋，token 与价值不成比" → 应对：分级策略基础盘极便宜；先 50/天试点，日报连续 3 天有真实发现才扩量。

## 七点五、收口修订（v2.1，2026-10-29 蜂群收口第1轮合入，实查复核通过）
> 实查：`findstr parent_session_id` 全 server 零命中（反驳①④属实）；`night10/gen_night10.py` 夜间批产真实存在（反驳⑤属实）。
1. **【采纳·反驳①】双重纸面依赖**：P4 回笼依赖的「成绩单/chat_report」尚未施工，工时估算为纸面叠加；P2 盲扫版不依赖任何未施工项，作为第一步。
2. **【采纳·反驳②】四问模板按对话类型分支**：代码类→查 git diff；绘图/批产类→查产出文件落盘（产物+日志）；闲聊/策划类→不做实证打分，只归类+标记"不可实证"，不进假完成清单，防假阳性淹没日报。
3. **【采纳·反驳③】标尺冲突仲裁**：巡检分不覆盖既有分。日报并排展示审核员/验证分（当时）与巡检分（事后），差 ≥30 分自动标"仲裁项"进日报头，人工裁决。
4. **【采纳·反驳④】P1 落点修正**：父子关系源头在前端 fan()/crew 派窗链路（6 类 SrcId），后端拿不到。施工=前端派窗显式上报 parent_session_id + 后端落库，前后端各半，P1 工时 1→1.5 天。
5. **【采纳·反驳⑤】调度错峰**：night10 深夜批产占用机器，巡检批跑改至清晨 05:00-07:00，并发仍≤8，仿 night10.lock 加 inspection.lock 互斥。
6. **【采纳·反驳⑥】验收加假阳性约束**：生效标准改为「连续 3 天：≥1 个与人工判断一致的真实未完成 + 抽检 10 条误报 ≤3（假阳性率<30%）」，两项同时满足。
7. **【采纳·进化师①】策划实查防线**：另立零代码任务——策划师提示词加强制「实查证据清单 ≥1 条文件行号/记录名」，无证据须标注"未经实查的推测"；不入本方案范围。
8. **【采纳·进化师②③】策划案索引 + 合并迁移**：建 `_策划案索引.md`（回笼案与本案互引标依赖）；P1 迁移若与回笼案同期施工，parent_session_id 与成绩单字段合并为同一次 sessions 迁移。

## 八、第2轮收口裁决（2026-10-29，v2.2 新增）
裁决原则修正：上轮"9条全采纳0驳回"被反驳师/进化师同时判为红队讨好症警报。本轮起，裁决须权衡成本与优先级，允许驳回。

**【采纳·反驳①+进化师1】红队强度校准**：课题池登记观察项——连续 3 次收口全采纳即触发"红队强度校准"课题（强制反驳师每轮产出 ≥1 条"不采纳建议"）。误报≤3 的判定人=人工复核，非巡检大师自判（堵"被考者当考官"）。

**【采纳·反驳②+策划师3】P3 加 token 供给前提**：昨夜 CodingPlan智谱 key 欠费全 429（code 1113）实证。P3 验收加两条：①连续 3 天实际完成率 ≥80% 才谈扩量；②批跑零成功→写告警文件（inspection_alert.txt）哨兵，防静默全失败。inspection.lock 只防巡检多开，不防与批产抢并发——遇 ComfyUI 卡图溢出 05:00 后，巡检主动让路（检测 night10.lock 仍存在则延迟启动）。

**【采纳·反驳③+策划师1】P2 盲扫版定位与验收改写**：盲扫数据源（agent_turns/git 反推）噪声最大，其价值=验证四问模板误报率，不是出体检日报。P2 验收写死为：**盲扫 20 条真实对话、人工复核误报率并出数据报告**（模板上线不证明任何东西）。盲扫日报每条强制标注「目标缺失，按对话首条用户消息推断」，防首批假阳性烧掉信任。

**【采纳·策划师2】分流判据机械化**：3 类分支（代码/闲聊/策划）用现成信号机械分流：有无 git diff / 有无工具调用记录 / 对话轮次。prompt 内禁止"视情况而定"表述。

**【采纳·进化师②③】执行追踪闭环**：`_策划案索引.md` 本次散会前已建（本条即兑现）；课题池条目加认领状态字段（待认领/进行中/已落地），每次蜂群收口扫一遍待认领项向用户汇报派单。
