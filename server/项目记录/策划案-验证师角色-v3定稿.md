# 策划案：新增「验证师」角色（终验官）

> 版本：v3 定稿（覆盖此前版本 v2，v2 位于本项目记录同目录，以本文件为准）
> 日期：2026-10-27
> 用户已锁定参数：位置在审核员之后；只看结果是否符合用户问题预期，不看过程。

## 一、定位与动机

现有流水线（系统分组 g1790260194938，已实查 roles_db.json）：
**策划师(5) → 施工队(6) → 反驳师(6.5) → 进化师(6.75) → 审核员(7) → 总结师(11)**

缺口：审核员把关的是过程与文本质量；链条末端没有人站在**用户视角做终验**——最终交付是否真的解决了用户最初的问题。

验证师 = **终验官**：不复盘中途过程，只拿「用户原始问题预期」与「最终交付结果」逐条比对，回答唯一问题——"这结果能不能交给用户？"

新链条：**策划 → 施工 → 反驳 → 进化 → 审核 → 验证(7.5) → 总结**

| 头像 | 🧪 |

## 三、Prompt 草案

> 你是一名「验证师」，多角色小组的最后一道关口。你不在乎过程，只看结果：前序角色给出的最终产出，是否真正解决了用户的原始问题、符合用户预期。
>
> 工作方法：
> 1. 先复述用户原始问题/需求，明确"用户到底要什么"（预期清单）。
> 2. 拿最终结果逐条对照预期清单，判定：✅ 符合 / ❌ 不符合 / ⚠️ 部分符合，每条给出对照依据（引用结果中的具体内容，必要时用工具实测查证）。
> 3. 给出终验结论：可交付 / 不可交付（不可交付时列明缺什么、建议退回给谁补）。
> 4. 【落盘规范】终验结论必须用 project_record(action=write, name="验证/主题名") 存入专属分区「验证」，格式对齐「审核」分区惯例。
>
> 禁止评价中间过程谁做得好谁做得差（那是审核员的事）；禁止讨论方案优劣；你的唯一标尺是"用户的原始问题预期"。语气直接，结论明确，不含糊。

## 四、与相邻角色的边界

| 角色 | 关注点 | 验证师区别 |
|---|---|---|
| 反驳师 | 逻辑漏洞、找反例 | 不做逻辑批判 |
| 审核员 | 过程质量、文本把关（评分制） | 不审过程，只比对"问题 vs 结果"（二值结论） |
| 总结师 | 收尾输出 | 验证师结论是总结师前置输入：不可交付则退回，不进入总结 |

## 五、任务计划（实施步骤）

1. 【配置写入】向 `private/roles_db.json` roles 数组追加验证师节点（id=`r`+13位时间戳，created_at/updated_at 与现有格式一致，order=7.5，avatar 🧪，chat_skin coppergray，prompt 用第三节草案）。依赖：无。
2. 【读回校验】读回 roles_db.json：JSON 可解析、order 位置正确、无破坏现有角色。依赖：步骤1。
3. 【宏扩展（可选）】`private/用户设置/macro_lib.json` 中"三师流水线"宏扩为"四师流水线"加验证步骤。依赖：步骤1。可与2并行。
4. 【界面实测】用户在角色管理界面确认显示位置/头像/皮肤；拉进真实任务对话实测一轮发言风格，必要时微调 prompt。依赖：步骤2。
5. 【二期（暂缓）】后台 swarm_pipeline.py 阶段编排接入（涉及核心代码，仅前端宏链路不满足时再做）。

## 六、实现方法与坑

- 步骤1 用 python json.load → 追加节点 → json.dump(ensure_ascii=False, indent=2)，避免手拼 JSON 文本出错。
- 坑①：roles_db.json 是运行时读写文件，服务端可能有缓存——写入后如界面未显示，提示重启/强刷。
- 坑②：prompt 含换行与引号，必须走 JSON 转义（\n），不要手拼字符串。
- 坑③：order 用 7.5 而非 7.05，避免未来在 7~7.1 间再插角色时拥挤。
- 步骤4 验收标准：新任务对话中验证师发言含「预期清单→逐条对照→可交付/不可交付」三段结构，且未跑题评价过程。

## 七、愿景

流水线形成完整闭环：策划出案 → 反驳攻案 → 施工 → 审核评质 → **验证终验（用户预期对齐）** → 总结收尾。理想形态下，任何"AI 声称完成但用户觉得没解决"的错位在交付前被拦截；验证分区沉淀的「预期 vs 结果」记录，长期可反哺策划师（常被漏掉的预期类型）与审核员（常错点清单），二期可向后台编排、验证触发分级（涉 server/ 必跑、纯问答跳过）扩展。

## 八、风险与备选

- 风险1：roles_db.json 写坏 → 角色系统不可用。应对：写入自动 .bak；步骤2 读回校验兜底。
- 风险2：验证师与审核员职责观感重叠。应对：prompt 强约束"只比对结果 vs 预期"；实测发言若雷同则收紧禁令条款。
- 风险3：沦为橡皮图章（永远"可交付"）。应对：prompt 要求 ⚠️/❌ 必须给出具体缺失项；后续可加淘汰线（连续 N 次全通过则收缩为手动触发）。
- 备选：若希望验证师有否决权插到审核前，order 改 6.9 即可，其余方案不变（用户已定审核后，仅留档）。

## 十、反驳项

- 反1：验证师与审核员可能输出雷同、成为冗余角色 → 应对：prompt 唯一标尺锁死"用户预期 vs 结果"，输出二值结论而非评分，实测一轮后按雷同度收紧禁令。
- 反2：验证师没有工具权限或上下文时只能凭文本"假验证"，反而制造虚假通过感 → 应对：prompt 明确"无法实测时必须声明仅文本比对，结论降级为⚠️"；二期再考虑给独立工具集。
- 反3：roles_db.json 运行时被服务端并发覆写，插入丢失 → 应对：写入前 python 原子读改写、写入后立即读回校验，界面未显示则提示重启。
