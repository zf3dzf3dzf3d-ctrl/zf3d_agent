# 策划案：对话级打分 + 回笼优化机制（进化阶段五→六攻坚）

> 版本：v1
> 日期：2026-10-29
> 前置实查（非推测）：roles_db.json 角色链 = 策划师(5)→施工队(6)→反驳师(6.5)→进化师(6.75)→审核员(7)→验证师(7.5)→总结师(11)，前端驱动于 public/js/agent-01-project-memory.js；评分解析器 server/score_parser.py 的【自评】已于 2026-10-17 停用；总结师为"新开对话+素材包"三模式沉淀，不判断任务真伪完成。

## 一、问题定义（痛点根源）

用户场景：一个对话派出多个角色，做完了，总结师关闭了所有，但任务实际根本没完成。

实查定位出三个结构性缺口：

1. **单向链**：验证师/审核员的 ❌/不可交付 结论没有回退通道——判了不可交付，流程照样走到总结师、照样关闭。
2. **评分空缺**：score_parser.py 自评机制被停用后，没有任何"这个对话任务完成度打几分"的量化记录；总结师沉淀的是经验，不是完成度。
3. **关闭无闸门**：总结师关闭动作只要求"有一次提问+一次答复"，从不校验"验收清单是否逐条达成"。关窗 = 事实上的"完成"，假完成由此产生。

## 二、方案总览：给每个对话加「回笼闸门」

核心思想：**关闭不是权利，是通过终验后的奖励。**

```
策划(出预期清单) → 施工 → 反驳 → 进化 → 审核 → 验证
                                        ↑          │
                              不可交付 ←───────────┘（回笼）
                                        │
                              验证通过 → 总结师 → 关闭
```

新增三个机制（均不推翻现有角色链，做增量）：

### 机制 1：预期清单强制化（策划师 prompt 增量）
- 策划师产出末尾必须附「【预期清单】」编号列表（3~8 条，每条可独立判定真伪）。
- 该清单随素材包一路带到验证师，作为终验的唯一标尺（验证师 prompt 已有此逻辑，缺的是"清单必须存在"的强制）。

### 机制 2：验证回笼（关键新增）
- 验证师结论格式扩展：`【终验】可交付` 或 `【终验】不可交付|退回:<角色>|补做:<缺什么>`。
- 前端 actions（agent-01-project-memory.js）监听终验标记：
  - 可交付 → 放行总结师（现状）。
  - 不可交付 → 自动弹出「回笼卡」：显示退回对象+缺失项，一键"派 <角色> 返工"（复用现有 fan()/素材包注入机制，把验证师结论+原预期清单打包为返工素材包）。
- 回笼次数记录在对话上；**回笼 ≥2 次仍不可交付 → 升级为人工介入提示**（toast+高亮），不无限自循环。

### 机制 3：对话完成度打分（评分回归，吸取自评失败教训）
- 自评停用的教训：让执行者自评 = 既当运动员又当裁判，输出被用户判定无用。
- 改为**验证师终验时顺带打分**（终验本来就是独立裁判）：`【终验评分】完成度 6/10 | 按预期清单 4/6 条达成`。
- 落盘沿用 data/self_scores.jsonl（score_parser.record 语义），box_id 关联对话，后续可做趋势分析（哪些对话类型假完成率高）。

### 机制 4：关闭闸门（总结师前置校验）
- 总结师启动前检查本对话最近一条【终验】标记：
  - 有「可交付」→ 正常进入总结（现状）。
  - 无终验记录（用户跳过验证师直接点总结）→ 弹确认框："本对话未经过终验，确定关闭？（关闭不代表任务完成）"。
  - 不可交付 → 阻断并引导走机制 2 回笼。

## 四、实施步骤（增量、不动核心链）

1. 【策划师 prompt】追加预期清单强制输出条款（roles_db.json 改 prompt，低成本）。
2. 【验证师 prompt】扩展输出格式：【终验】二值结论 + 【终验评分】（改 prompt）。
3. 【前端回笼卡】agent-01-project-memory.js：解析【终验】不可交付 → 弹回笼卡 → 一键派返工（复用素材包机制，中等成本，核心增量）。
4. 【关闭闸门】总结师入口加终验校验（同文件，小改）。
5. 【打分落盘】终验评分写入 self_scores.jsonl（score_parser.record 复用，小改）。
6. 【验证】跑一个故意做不完的任务实测：预期清单存在→验证师判不可交付→回笼卡出现→返工→二次终验→可交付→总结师放行。

## 五、风险与反驳

- 反1：回笼会不会无限循环烧 token？→ 机制2 已设回笼≥2 次升级人工，硬上限。
- 反2：验证师打分会不会重蹈自评覆辙（被打分角色与打分者是同一模型）？→ 有区别：自评是执行者自己打，终验是独立角色对照清单打，且有客观锚点（清单条数）。若仍失真，二期引入双验证师交叉。
- 反3：改 agent-01-project-memory.js 风险大？→ 只加监听和弹卡，不动 fan()/素材包注入现有逻辑；每步 git 快照可回滚。
- 反4：用户就想跳过验证直接关窗？→ 机制4 只弹确认不硬禁，尊重用户决定权，但留下"关闭≠完成"的明确警示。

## 六、推荐度评分（影响0.40+低成本0.25+低风险0.20+亮点0.15）

【推荐度】验证师 prompt 扩展（步骤2+5）88/100｜档位A
【推荐度】策划师预期清单强制（步骤1）85/100｜档位A
【推荐度】前端回笼卡+关闭闸门（步骤3+4）80/100｜档位A（核心价值所在，成本略高）
【推荐度】二期：双验证师交叉+假完成率趋势报表 60/100｜档位C

【策划师结论】先做 1+2+5（纯 prompt+落盘，半天量级），验证打分数据可信后，再上 3+4 前端闸门（1~2 天量级）。这样每一步都有实据可验，避免一次性大改。
