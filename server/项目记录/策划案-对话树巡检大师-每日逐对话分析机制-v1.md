# 策划案：对话树全量巡检大师（主对话+孩子逐个分析机制）v1
日期：2026-10-29

## 一、目标
设一个"对话树巡检大师"（新角色或进化师分支），每天自动遍历所有对话树（主对话→孩子窗），逐个对话分析打分，产出《巡检日报》+《问题清单》，把"事后救火"变成"每日体检"，日跑约 200 个对话。

## 二、数据基础（本轮实查结论）
- `server/db.py`：SQLite 存 sessions + chat_history，chat_history 已有 parent_id（问答对级）；关闭对话转入 chat_history_archive（不丢）。
- 画布子窗关系：6 类孩子窗靠前端 `el._xxxSrcId` 识别（_summarizerSrcId/_qcSrcId/_thinkerSrcId/_customSrcId/_expertSrcId/_raceSrcId，agent-01-project-memory.js:2021），**父→孩子的树关系目前主要在前端 DOM 层，未持久化成数据库树** —— 这是本机制最大的前置补课项。
- 评分现状：审核员评分只在蜂群流水线内有（swarm_pipeline），前台独立对话无对话级分。

## 三、机制设计
1. **对话树持久化（P1 前置）**：sessions 表加 `parent_session_id` 列；派孩子窗时后端同步写入，形成可查的主+孩子树。没有这一步，巡检只能逐窗盲扫，认不出树。
2. **巡检大师角色（P2）**：
   - 输入：一棵对话树 = 主对话 goal + 各孩子窗的 chat_report（配合上一份"回笼策划案"的成绩单）或原始 chat_history。
   - 分析模板（每对话固定四问）：①任务目标是什么？②实际完成了什么（有无 git diff/文件产出实证）？③完成度打分 0-100（证据锚定，不听自报）？④失败归因：策划错 / 施工假完成 / 审核放水 / 上下文断裂 / 工具障碍？
   - 产出：per-对话一行记录 → daily_inspection.jsonl，汇总成《巡检日报》。
3. **日跑 200 个（P3 调度）**：复用 schedule 定时任务 + 车道并发闸门（现成 8~10 并发）。每个对话分析约 3~5k token，200 个/天 ≈ 1M token/天，建议策略：**全量只跑轻量摘要级（便宜模型），发现可疑（低分/自报与证据矛盾）才升级深分析**，成本可控。
4. **修复闭环（P4）**：
   - 可修复问题（漏做、未验证）→ 开"回笼"子对话重做；
   - 系统性问题（同一根因复现 ≥3 次）→ 自动入进化师课题池（现成机制）；
   - 巡检结果回流到提示词优化建议清单，人工拍板后改 prompt。

## 四、实施步骤
1. P1：sessions 加 parent_session_id + 派窗链路写入（1 天）
2. P2：巡检大师角色定义（roles_db 新角色 order=6.9）+ 分析 prompt（0.5 天）
3. P3：schedule 定时任务 + 分级分析调度（1 天）
4. P4：问题清单 → 课题池 → 回笼联动（1 天）
验收：跑一天后日报能指出 ≥1 个真实未完成任务，且与人工判断一致。

## 五、风险
- 分析权≠修改权：巡检大师只读+建议，禁止直接改对话/代码（防重演 chat_manage 误关窗事故）。
- 深夜批跑要过车道闸门，避免挤占用户实时请求。
