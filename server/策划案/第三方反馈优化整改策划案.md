# 策划案：第三方反馈优化整改（v1）
> 版本：v1（2026-10-28），覆盖此前无版本记录。依据：用户收到的第三方（5.6.0 官方版）使用反馈三张截图 + 原对话第 1 轮 AI 评估结论。

## 〇、背景与定性
第三方反馈针对的是**上游 5.6.0 官方版**，大部分问题（打包缺 Python 包、写死本机路径、private 私货入库、0.0.0.0 无鉴权、CRLF、approval_mode 出厂 full_access、db 写锁 30 秒、中转 404 被兜底吞掉等）在 5.7.0 已逐条修复并有 lessons/安全基线佐证。真正遗留、值得开工的只有 3 类：
- A. i18n 缺词条（反馈称切英文 20 次错 10 次、927 处无英文词条）
- B. 代码卫生（死代码：`fps_crive if False else fps_crime`、`style="transparent;..."` 等）
- C. 交互吐槽（线路强占默认模型、全屏遮罩、写死气泡文案——主观，仅备查）

## 一、任务计划（三阶段，串行依赖）
**阶段 1：摸底实测（半天）**
1.1 i18n 词典全量扫描：python 脚本对 public/js/i18n-data.js / i18n-data-extra.js 与前端硬编码中文做交叉统计，得出本仓真实缺词条数量与分布热力图（验证「927 处」口径）。
1.2 死代码扫描：全仓 grep `if False`、`style="transparent;`、`fps_crive` 等模式，输出清单（文件:行号）。
1.3 产出物：`策划案/反馈整改-摸底清单.md`。

**阶段 2：分批整改（依赖阶段 1 清单）**
2.1 i18n 高频词条补齐（先修用户可见高频页面：输入框、菜单、工作台、设置页；低频长尾标注 TODO 暂缓）。
2.2 死代码删除（每处删除前确认无引用，语法校验，git 精确暂存）。
2.3 交互吐槽项：不主动改，单独立 backlog，用户点名才做。

**阶段 3：验证与沉淀**
3.1 切英文实测：主流程（发消息/开工作台/设置）走查，错误率目标 <2%。
3.2 回归：中文模式零变化（词条只增不删主词典结构）。
3.3 沉淀到 project_record 并关闭。

## 二、实现方法与坑
- i18n 扫描用 `F:\...\python\python.exe` 脚本批量 grep，禁止逐文件手读。
- 补词条只改 i18n-data.js（主词典），不动 extra；改完升 index.html 缓存号（历史惯例 ?v=N）。
- 死代码删除走「查引用→删→语法校验→逐文件 git add→commit」纪律，禁止 add -A。
- 坑：①部分「中文」是注释/日志非 UI，需排除，否则虚增工作量；②i18n-data-extra.js 745KB 属大文件懒加载 backlog（另案），本次不合并、不扩大战线；③「927 处」是第三方对 5.6.0 的口径，5.7.0 需重测，不能照抄。

## 三、愿景
英文模式可用率达到准生产水平（主流程零报错词条），代码库无已知死代码；第三方反馈全部条目在 5.7.0 形成「已修/已整改/已记录不修」三态闭环台账，任何后续反馈可直接对账。

## 四、风险与备选
- R1 词条量超预期（>500 处）→ 按页面热度分批，只做 P0 页面，长尾挂 backlog。
- R2 删死代码误伤（看似死实被动态 eval 引用）→ 删除前全仓搜引用串，.bak 自动备份可回滚。
- R3 与并行会话冲突（本仓常有并行改动）→ git 精确暂存逐文件 add，动前先 git status。
- 备选降级：若全量补齐成本过高，只修「报错级缺词」（补齐会触发 console 报错的缺失 key），其余不翻译回退中文，成本降一个量级。
