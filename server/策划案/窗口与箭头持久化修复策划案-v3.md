## 〇-2、A1 实验定罪结果（2026-10-30 已完成）
- 实验方法：按 UserSettings.flushToServer 同格式直接 POST {changes:{zf3d_canvas_arrows:[...]}} → 返回 200 且 user_settings.json 实测出现该键（回读值逐字一致）→ 测试后置 null 清理，回读确认键已删。
- **定罪结论：服务端链路无罪。** 白名单嫌疑❌（POST 接受任意键，mixin_settings_user.py:60-100 仅限制单值 256KB/键总数 500，当前 142 键远未触顶）、键数裁剪嫌疑❌、写竞态嫌疑❌（无此机制，裁决②一致）。
- **唯一剩余嫌疑：前端从未发出 POST——即快照记录时用户确实没画过箭头**（"箭头丢失"是伪问题的概率大幅上升）。B 阶段照做（软删除有独立价值）；A2 的 saveAll 本身经查无防抖吞改动问题，收缩为仅加 beforeunload sendBeacon flush（A3），不重写保存链路。
- 遗留动作：需用户下次真实画箭头后重启实测一次（C 阶段回归覆盖），若仍丢再回来复诊。
1. **箭头未持久化**：user_settings.json 对 zf3d_canvas_arrows 0 命中属实，但"保存链路从未成功"是推断而非定论（快照时可能本无箭头）。→ A1 实验定罪。
2. **窗口删除不可恢复**：api_dispatch_delete.py:82 物理 DELETE、trash_items 无记录，属实；但 3 窗是否经此接口丢失无日志证据。→ 软删除作为防御性修复，真实丢因在 A1 一并排查。
3. /api/user-settings GET/POST 可复用（api_dispatch_get.py:904）。

## 二、任务计划（A、B 可并行，C 依赖 A、B）
### 阶段 A：箭头持久化（第一优先）
- **A1 最小实验定罪（0.5d，第一动作）**：浏览器画 1 个箭头 → 立即查 localStorage 与 user_settings.json → 四种嫌疑对照：①POST 未发出（抓请求）②服务端白名单拒收（读 api_dispatch POST 源码白名单）③storage-guard 清理 ④写竞态（复现实验）。同时查 server 日志有无 3 窗的 delete 调用痕迹。
- **A2 修复（0.5d，按 A1 定罪结果二选一）**：
  - 若白名单拒收/覆盖写有问题 → **首选路线：箭头改存 DB 专表 canvas_arrows（照 canvas_nodes 模式）+ 专用 GET/POST 接口**（收口裁决④，一次到位）；
  - 若仅是前端漏发/防抖吞改动 → 保留 UserSettings 路线，加写后读校验 + beforeunload sendBeacon 强制 flush。
- ~~refresh _dirty~~：仅当 A1 实验复现"写竞态"才做，否则不做（裁决②）。

### 阶段 B：窗口软删除（防御性，可并行）
- **B1（0.5d）**：canvas_nodes 删除前留底。**方案（按裁决⑤修正）**：优先 ALTER TABLE trash_items ADD COLUMN data TEXT（幂等 IF NOT EXISTS 语义需 PRAGMA table_info 判断），canvas 行 source='canvas_nodes'、orig_path='canvas://node/<id>'、data=整行 JSON；只改 canvas_nodes 分支，改前 grep 调用点审计锁重入风险。
- **B2（0.5d）**：恢复逻辑走 trash.py 的 restore 模式适配：source=canvas_nodes 的行不搬文件，直接反序列化 data 重插 canvas_nodes（id 冲突生成新 id）。
- B3 前端回收站入口：暂缓（档位 C）。

### 阶段 C：回归验证（0.5d）
画多角度/多起止点箭头 ≥3 条 + 删 1 窗 → 重启 → 核对：①箭头位置角度原样恢复且落库可见 ②trash_items 有被删窗口行且能恢复 ③既有 22 窗坐标零变化。快照比对脚本复跑两次。

## 三、风险与备选
1. A1 实验发现箭头其实能正常落盘（伪问题）→ 阶段 A 收缩为仅加 A3 flush，如实向用户报告"箭头链路本身正常，此前丢失因快照时无箭头"。
2. trash_items 加列影响现有文件回收逻辑 → 新列 nullable，旧逻辑零感知。
3. beforeunload POST 中断 → sendBeacon → 退化防抖 100ms。
