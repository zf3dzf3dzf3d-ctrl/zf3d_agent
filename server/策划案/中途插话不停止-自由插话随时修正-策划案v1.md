# 策划案：中途插话不停止（自由插话随时修正）v1

> 功能口号：朱峰智能体又一次原创功能 —— 中途插话不停止功能：任何时候中途输入文字，自动插话，AI 会按你的参考修正工作，且**不会停止工作**。

---

## 一、现状分析（基于 5.7.0 实测代码）

### 1.1 现有两条循环通路

| 通路 | 文件 | 插话能力现状 |
|---|---|---|
| 浏览器主循环（默认） | `public/js/agent-02-loop-core.js` + `agent-00-send-status.js` | ①「排队」：AI 回复中用户发消息进 `chat.queue`，**等本轮任务结束才发送**；②「鞭子」：`chat._whipRequested` 固定文案催促收尾，下一个工具请求注入。**缺自由文本插话** |
| 服务端内核循环（Loop-S，阶段B，未切默认） | `server/loop_s.py` | 有 `stop_flag` 停止通道（`request_stop`），**没有插话通道** |

### 1.2 关键差距
- 现有「鞭子」是**硬编码文案**（只能催收尾），用户**不能自定义插话内容**（如"改用方案B"、"那个路径写错了"、"优先做XX"）。
- 排队机制会**停止当前工作流**（等结束后当新任务跑），不符合"不停止、即时修正"。
- Loop-S 内核无任何插话入口。

### 1.3 可复用的现成机制（本方案的核心是"两个小改动"而非新造轮子）
1. **步数预算注入**（agent-02-loop-core.js L236-266）：每轮 depth 判断后 `messages.push({role:'user', content:'（系统提醒·不回复此条）…'})` —— 这就是插话注入的现成插入点。
2. **鞭子消费机制**（L268-277）：`chat._whipRequested` 一次性消费 flag —— 把它泛化为 `chat._injectQueue[]` 即可承载任意文本。
3. **stop_flag 通道**（loop_s.py L290-298）+ 事件流 SSE —— 服务端插话通道照此模型加 `inject_queue`。

## 二、功能定义

### 2.1 用户体验
- AI 正在工作中（转圈/调用工具/长任务），用户随时在输入框打字回车。
- 消息**立即以"插话气泡"形式出现在聊天流**（带 ⚡ 插话标记），AI **不停止当前任务**。
- 最迟在**下一个模型请求**（即当前工具执行完、下一次调模型前），插话原文被注入上下文，AI 按插话修正后续工作。
- AI 被要求：**必须响应插话但不得中断主任务**；插话与主任务冲突时以插话为准修正方向。

### 2.2 与现有机制的关系
| 机制 | 行为 | 保留/升级 |
|---|---|---|
| 鞭子 | 固定催收尾文案 | 保留，改为 `_injectQueue` 的一种快捷预设 |
| 排队 | 任务结束后发新消息 | 保留，用户显式选「排队发送」时走旧路 |
| **自由插话（新增，默认开启）** | 立即注入，不停止 | ★ 本案核心 |

## 三、技术方案

### 3.1 前端（浏览器主循环，改动最小、先落地）

**① 入队（发送拦截）— `agent-00-send-status.js`**
- `send()` 中判断 `chat._busy && !chat._stopped && 设置.自由插话开启` → 不进 `chat.queue`，改调 `chat._injectQueue.push({text, ts, images?})`。
- UI：聊天流渲染「⚡ 用户插话」气泡（新 msg type `inject`），打字机行上加插话按钮（复用鞭子按钮位，长按弹出输入框发自由插话）。

**② 消费（循环注入点）— `agent-02-loop-core.js` 每轮深度循环开头**
```js
// ===== 自由插话注入（一次性消费，位于鞭子注入之前） =====
if (chat._injectQueue && chat._injectQueue.length) {
    var _inj = chat._injectQueue.splice(0);   // 全部消费
    _inj.forEach(function(m){
        messages.push({ role: 'user',
            content: '（用户中途插话·务必响应·不要因此中断当前任务）' + m.text });
    });
    try { Store.addLog('info', chat.id, 'inject-consume',
        '自由插话注入 ' + _inj.length + ' 条 | depth=' + depth); } catch(e){}
}
```
- 放在 L268 鞭子注入同层，**每次调模型前**生效 → 注入延迟 = 一次工具调用时长。

**③ 防丢失兜底**
- `chat._injectQueue` 挂在 chat 对象上，随 Store 持久化（与 queue 同待遇），刷新页面不丢。
- 若任务在插话后 30 秒内结束（没机会消费），出队逻辑把残留插话自动转为下一条普通用户消息（走 _onSendComplete 队列分支）。

### 3.2 系统提示词补充（全局提示词加一段）
```
【用户中途插话协议】对话中可能收到以「（用户中途插话·务必响应·不要因此中断当前任务）」
开头的 user 消息：这是用户在你工作期间发来的即时修正。你必须：
1. 立即按插话内容修正当前工作方向/参数/结论；
2. 不要停下、不要重新开始任务、不要复述插话全文；
3. 在下一个可见输出中简短确认已收到插话（如"收到，已改为…"）。
```

### 3.3 服务端内核 Loop-S（阶段二，对齐内核化路线）

照 `request_stop` 模型加插话通道，`loop_s.py`：
```python
# run dict 增加：'inject_queue': []（受 run['lock'] 保护）

def request_inject(run_id, text):
    run = get_run(run_id)
    if run is None: return False
    with run['lock']:
        run.setdefault('inject_queue', []).append({'text': str(text or ''), 'ts': time.time()})
    _emit(run, 'inject_queued', {'len': len(run['inject_queue'])})
    return True
```
- `run_loop_s` 主循环每轮调模型前：`with run['lock']: batch = run['inject_queue'].splice(0)`，逐条 `msgs.append({'role':'user','content': INSERT_PREFIX + text})`，并 `_emit(run, 'inject_consumed', {...})`。
- 路由：`routes/api_dispatch_post.py` 加 `POST /api/loop_s/inject`（body: run_id + text），`mixin_loop_s.py` 加 handler。
- 前端 SSE 订阅者已能收到 `inject_queued/inject_consumed` 事件，用于 UI 气泡状态同步。

### 3.4 设置项
- `设置 → 对话`：新增开关「中途插话不停止（默认开）」+ 行为选择：
  - `注入模式`（推荐，本方案）：立即注入修正；
  - `排队模式`（旧行为）：任务结束后再发。
- 开关只影响前端发送拦截分支，不影响 Loop-S 通道（Loop-S 通道常开）。

## 四、交互细节

| 场景 | 表现 |
|---|---|
| 用户在 AI 工作中发消息 | 气泡立即上屏，标 ⚡「已插话 · 下一步生效」；工具球动画不中断 |
| 插话被消费 | 气泡状态变「已注入 ✓」，日志 inject-consume |
| AI 响应 | 下一轮文本输出开头自然确认修正 |
| 连发多条插话 | 全部一次性注入（按时间顺序），AI 按最后意图执行、前面作为上下文 |
| 插话含图片 | 首版仅支持文本（多模态插话列为二期） |
| 任务已结束才发的消息 | 走普通发送（不标记插话） |

**防滥用/防失控**：
- 单轮插话队列上限 10 条，超出提示"合并后再发"。
- 插话注入文本带固定前缀，A16 消息清洗不受影响。
- 插话不会重置 depth、不会清空任务清单（task_list 状态保持）。

## 六、验收标准
1. AI 执行 20+ 步长任务途中发送 3 条不同插话：任务不中断（无 stop、无重新开始），每条插话在 ≤1 次工具调用后被注入，AI 输出体现修正。
2. 插话 30 秒后任务自行结束 → 残留插话自动作为普通消息发出，不丢失。
3. 刷新页面后再消费：`_injectQueue` 持久化不丢。
4. Loop-S 通道：dry_run 注入假模型场景下，inject → 消费 → SSE 事件端到端可见。
5. 老功能回归：鞭子、排队、停止按钮行为不变。

## 七、风险与对策
| 风险 | 对策 |
|---|---|
| 插话与 task_complete 竞态（注入瞬间任务终局） | 注入检查放在 stop/task_complete 拦截判定之后同一轮；残留转排队兜底 |
| 模型忽视插话 | 前缀强制「务必响应」+ 提示词协议 + 下轮审计日志（AI 首个可见输出是否提及）|
| 队列无限膨胀 | 上限 10 条 + UI 合并提示 |
| 与排队机制双入口打架 | 发送拦截只走一条分支，互斥清晰 |
