# 数据库读写优化策划案

> 调查范围：`server/` 全部 20 个涉及 SQLite 的模块
> 主库：`private/db/zf3d_canvas.db`（另含 memory.db / app.db / zf_data.db）
> 核心文件：`server/db.py`（681 行）、`server/config.py`（_TimeoutLock）

---

## 一、现状盘点

### 1.1 已做对的事（保持）
- **WAL 模式** + `busy_timeout=30000` + `synchronous=NORMAL`（db.py get_db，2026-09-22 已修复重复设 journal_mode 阻塞问题）
- **全局 `_TimeoutLock(5.0)`**：持锁超时告警 `[DB-SLOW]`，避免写事务泄漏导致全站卡死（config.py 216 行）
- **定期维护线程**：每 6h PASSIVE checkpoint + incremental_vacuum，>50MB 触发 VACUUM（db_maintenance）
- **破坏性操作前安全备份**：主库+WAL+SHM 一并备份到 `private/backups/`，最多留 6 份
- **损坏自恢复三级流程**：重试 → 温和恢复 → 备份留底后重建

### 1.2 主要问题点（按严重度排序）

| # | 问题 | 位置 | 影响 |
|---|------|------|------|
| P1 | **每次操作新建连接、用完即关**，无连接池/复用 | get_db 及全部调用方 | 每次连接开销 ~1-5ms，高频聊天/画布场景累计明显；PRAGMA 每连接重设（busy_timeout/synchronous/temp_store/cache_size 4 条 × 每次连接） |
| P2 | **get_db() 内嵌惰性建表**（_ensure_agent_turns + PRAGMA table_info） | db.py:320 | 虽有 `_AGENT_TURNS_READY` 旗标，但首个连接仍多查一次 table_info；逻辑混在"取连接"里，职责不清 |
| P3 | **20 个模块各自 `sqlite3.connect`，绕过 get_db**（zf3d_commands、trash、watchdog、token_usage_stats、api_dispatch_get_joined_check 等） | 各文件 | 连接参数不统一：timeout=5 vs 30；部分不走 WAL 参数；事务边界不一致 |
| P4 | **锁粒度粗**：部分调用 `with _db_lock` 包住整个"连接+查询+commit+close"，读操作也被全局串行化 | handler_tools_tasks.py 等 | 读多写少场景读吞吐被写锁拖累；WAL 模式本支持读写并发 |
| P5 | **异常路径可能漏关连接**：手写 try/except 中 conn.close() 散落多处，个别路径 commit 前异常会跳过 close | handler_tools_tasks.py:117-146 等 | 连接句柄泄漏 → Windows 上文件句柄占用 → WAL 无法 checkpoint |
| P6 | **write_agent_turn 吞掉所有异常**（except: 忽略） | db.py:257-270 | 落库失败无感知，重放恢复数据缺失时无从排查 |
| P7 | **agent_turns 无清理机制**，content 存全量文本（含工具结果大文本） | agent_turns 表 | 长期无限增长，拖慢 VACUUM 与查询 |
| P8 | **高频画布位置写入**：canvas_nodes 拖拽即写库（推测，updated_at 字段+前端实时保存模式） | canvas_nodes | 每次拖动 N 次写事务 |

## 二、优化方案

### 方案一（P1+P2）：线程本地连接复用【收益最大，改动小】
```
get_db() 改为 threading.local 缓存连接：
- 每线程首次连接时设一次全部 PRAGMA
- 提供 close_all() 供服务器关停时统一收口
- 连接加 sqlite3.connect(..., check_same_thread=False) 不需要——按线程隔离即可
```
- 预期收益：消除 90% 的连接建立开销；改动仅 db.py 一处
- 风险：低。WAL 模式下长连连接是官方推荐用法

### 方案二（P3）：统一 DB 入口
```
新增 db.execute(sql, params, write=False) / db.query(sql, params) 门面函数：
- 内部处理连接、锁、commit、close/异常兜底
- 逐步迁移 20 个散点模块（先迁 zf3d_commands、trash、watchdog 三个高频文件）
- 过渡期保留 sqlite3.connect 直连，不强制一次改完
```

### 方案三（P4+P5）：读锁分离 + with 语句兜底
```
- 读操作不再抢 _db_lock（WAL 本就允许读写并发），仅写操作持锁
- 所有 conn 使用改为 contextlib.closing(sqlite3.connect(...)) 结构，杜绝句柄泄漏
```

### 方案四（P6+P7）：agent_turns 治理
```
- write_agent_turn 失败改为计数告警（连续失败 N 次打 WARN，不影响主流程）
- 定期维护中追加：DELETE FROM agent_turns WHERE created_at < now-30天（阈值可配置）
- content 超大（>64KB）时截断或转存文件，表内只存路径
```

### 方案五（P8）：画布写入防抖
```
- 前端拖拽结束（mouseup / 300ms 防抖）才发保存请求；后端对同节点位置更新做 500ms 合并
- 若已有防抖则此条跳过（需前端确认）
```

## 三、实施计划

| 阶段 | 内容 | 工作量 | 风险 |
|------|------|--------|------|
| 第 1 步 | 方案一：get_db 线程本地连接 | 0.5h | 低，收益最大，先做 |
| 第 2 步 | 方案三：conn 泄漏加固 + 读不持锁 | 1h | 低-中，需回归测试登录/画布 |
| 第 3 步 | 方案四：agent_turns 清理+告警 | 1h | 低 |
| 第 4 步 | 方案二：db 门面 + 迁移高频模块 | 3-4h | 中，分批迁移 |
| 第 5 步 | 方案五：画布防抖（与前端确认后） | 1h | 低 |

**验收标准**：
- 登录/画布请求 P95 延迟不劣化（建议压测对比）
- `[DB-SLOW]` 告警零出现
- 连续运行 48h 后 agent_turns 表大小有界
- 备份/恢复流程回归通过

---

## 四、暂不建议做的
- ❌ 换 PostgreSQL/MySQL：单机单用户场景 SQLite 足够，迁移成本远大于收益
- ❌ ORM 引入：现有 SQL 简单直白，ORM 反而增加黑盒
- ❌ 读写分离多库：数据量（当前 <1MB）远未到瓶颈
