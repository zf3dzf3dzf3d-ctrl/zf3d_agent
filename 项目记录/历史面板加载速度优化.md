
## 2025-08-27 历史面板加载速度优化(按天分页)

### 问题
对话状态右侧历史面板打开极慢。根因:`/api/db/chat-history/all` 一次性返回全部 user 消息**完整内容**(实测 209 条 / 约 1.9MB JSON,单条最大 33 万字符),前端还把所有对话全部渲染进 DOM 再靠 CSS 隐藏。

### 方案
- 后端(`server/handler_routes.py`):
  - `/api/db/chat-history/all` 默认改为**按天分组**:每天返回前 5 条(仅元数据 + 200 字符内容前缀)+ 当天总数,实测响应 2KB / 41ms(原 1873KB)。
  - 新增按天分页参数:`?day=YYYY-MM-DD&offset=N&limit=5`,每次取 5 条。
  - SQL 不再 SELECT 整段 content,元数据查询用 `LENGTH(content)`;内容前缀用 `substr(content,1,200)` 单条提取(新增辅助方法 `_chat_history_content_prefix`)。
- 前端(`public/js/app-taskpanel.js`):
  - `_loadHistoryPanel` 改调 `?initial=5`;`_renderHistoryPanel` 按天渲染,每天只建 5 个 DOM 节点。
  - 新增 `_loadMoreHistoryForDay`:点"加载更多(剩余 N 个)"每次向服务器取 5 条增量插入。
  - 新增 `_buildHistoryConversation`:单条对话构造(时间 + 内容前缀 60 字 + ↗续聊按钮)。
  - 日期标题只显示当天对话数,去掉整体数量统计。
  - `_loadModelPanel`(大模型统计)同步适配:只按 day=今天 分页拉取今日数据,不再全量拉历史。

### 兼容性说明
- 旧接口 `chat-history/sessions` 分支已并入 `all`(原前端就没人调 sessions,行为一致)。
- 历史对话的"勾选多条续聊"交互简化为单条 ↗ 续聊(原来依赖全量 questions 数据,已不再返回)。
- 文件已自动备份 .bak;`_loadHistoryRecords` 属性保留但不再使用。

### 验证
- 后端单测:初始接口 2KB/41ms,分页接口 0.9KB,<5ms;非法 day 参数正确报错。
- 前端逻辑模拟(node):首屏每天 5 条、连续 3 次加载更多 5→10→15、剩余计数正确。
