# 对比总结：本方案（Python+浏览器 2D 引擎）vs Unity vs 原 fight 项目

## 一、三个方案对比

| 维度 | 本方案（py-browser-2d） | Unity | 原 fight 项目（C# 硬骨骼自研） |
|---|---|---|---|
| 启动/迭代速度 | 秒级：改完刷新即生效，无需编译 | 每次改 C# 需 Domain Reload，编辑器重 | 同 Unity |
| 渲染上限 | WebGL2 instancing，实测 2 万实例单 draw call；万人骨骼 CPU 侧仅 1.6ms/帧 | 高（SRP Batcher/GPU instancing），上限更高但配置复杂 | 高（自研硬骨骼撑过万人） |
| 架构复杂度 | 极简：SoA 数组 + 自动池化 + 单渲染器，全核心 ~4 个文件 | 庞大：组件模型易失控（正是原项目"混乱"的根源） | 中：自研但组件/事件系统膨胀 |
| 对象池/事件 | 语言级解决：实体=数组下标，死亡即回收，无手写池无事件总线 | 需手写或买插件 | 手写且膨胀失控 |
| 2D 骨骼 | 自有 JSON 格式，5 关键帧硬骨骼已验证；Spine 无必要 | Spine/Anima2 官方支持好 | 自研硬骨骼 |
| 生态/资产 | 几乎为零 | 巨大 | 自有积累 |
| Steam 发布 | 需 WebView2/CEF 壳打包（见下） | 原生支持，一键 | 原生支持 |

## 二、万人同屏结论（步骤5实测）
- 1 万骨骼单位：CPU 每帧 1.636ms（预算 9.9%），GPU 单 draw call → **可行**，且余量足。
- 2 万单位 3.279ms 依然从容。详细数据见 `docs/bench_report.md`。
- 结论：**硬骨骼路线在 Web 上完全成立，Spine/软骨骼在万级同屏场景不仅无必要而且是负优化。**

## 三、架构结论（回应"开发混乱"痛点）
原 fight 项目的问题是组件+事件系统+手写对象池三层抽象互相缠绕。本方案用三条铁律规避：
1. **数据驱动**：实体就是 SoA 数组下标，没有 GameObject，没有 AddComponent。
2. **自动池化**：spawn 复用死亡槽位，池化是数组语义的自然结果，不是维护的系统。
3. **无事件总线**：需要通信的地方直接读写数组，逻辑顺序用代码顺序表达。

代价是失去编辑器可视化与生态；换来的是**全项目核心代码 <500 行、无黑魔法、AI 可全文理解与修改**。

## 四、Steam 发布路径
可行，无需 Node：
1. **WebView2 壳（推荐）**：Windows 自带运行时，Python 侧用 `pywebview` 或原生 WebView2 窗口加载本地 server，几十行代码；Python 可用 PyInstaller 打包为单 exe。
2. **轻量 CEF/Electron 替代**：Tauri（Rust 壳，体积小）亦可，但不必要。
3. 注意点：Steam 覆盖安装需处理端口占用（或改用本地管道/文件通信）；Python 打包体积 ~30-50MB。

## 五、最终建议：是否值得迁移？
**分场景**：
- 若目标是"万级同屏 + 规则驱动的大规模战斗"，且迭代速度/AI 协作优先 → **值得迁移**，本原型已验证全部关键技术点（性能、骨骼、架构、发布路径）。
- 若依赖 Unity 生态资产、需要复杂编辑器工作流、团队多人协作 → 留在 Unity，把"数据驱动+自动池化"的架构教训带过去。

技术验证全部通过，下一步若立项，先迁移 fight 项目的一个完整战斗场景做 A/B 实测。
