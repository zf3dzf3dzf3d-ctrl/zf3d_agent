# Bug 五师策划案 —— 老问题复发终结机制

> 目标：让"同一个 Bug 反复出现"从制度上被终结。不是加五个名字，而是建一条**闭环流水线**，每个师堵住复发链条上的一环。

---

## 一、老问题为什么反复出现？（根因诊断）

复盘本项目历史（i应用窗口修复、undefined文件Bug、缓存号漏升、双副本漂移、z-index 遮挡等），复发有 5 个根因，正好一一对应五个师：

| 复发根因 | 案例 | 对应防线 |
|---|---|---|
| ① 修了表象没修根因（打地鼠） | 窗口逐个加 CSS，不补通用基类 | Bug拆解师 |
| ② 定位靠猜，错误归因被记录并继承 | 死锁事件十几个会话都在改密钥/锁 | Bug定位师 |
| ③ 修复了但没验证"运行时真生效" | 改了 server/public 过时副本 | Bug修复师 |
| ④ 修好了但没有沉淀成"免疫规则"，下次会话不知道 | 同类坑每次重新踩 | Bug排查师 |
| ⑤ 修复本身引入新问题 / 补丁越叠越烂 | 巨大 z-index 补丁 | Bug优化师 |

---

## 二、五师职责定义

### 🐛 Bug修复师（前线动手）
- **职责**：拿到定位师的根因结论后实施修复。铁律：只按已实证的根因改，禁止凭猜测打补丁；改动最小化，每次修复必须附"根因一句话"。
- **产出**：修复代码 + 根因声明 + 触发条件说明。
- **红线**：根因未定位确认（无栈/无实验证据）时拒绝动手，退回定位师。

### 🎯 Bug定位师（找根因）
- **职责**：钉死根因，产出可复现的因果链。强制执行全局纪律第五条三条铁律：栈优先（py-spy dump）、二分隔离（A通B不通必列差异点做对照实验）、前提复核（跨3会话的bug先独立实测前结论）。
- **产出**：定位报告（现象→因果链→根因→证据文件行号），写入 project_record「定位/」分区。
- **红线**：不允许"可能大概"式结论；归因到某个 commit 必须能解释时间差，否则不许宣布。

### 🔍 Bug排查师（复发检测+免疫沉淀）
- **职责**（本机制的核心增量）：
  1. **复发巡检**：每次修复收口后，用关键词在 project_record 历史里检索同类 Bug，确认不是"换皮复发"；
  2. **全局扫雷**：按本次根因模式全局搜索同类隐患点（如发现某窗口缺定位基类，立即检查其余全部窗口）；
  3. **免疫卡登记**：把根因写成"免疫规则"存入 project_record「免疫卡/」分区，格式固定，供所有会话开工时检索。
- **产出**：扫雷清单（同类隐患 N 处，已修/挂账）+ 免疫卡。
- **红线**：免疫卡必须含"症状特征→第一步检查什么"的可执行指引，不许写空话。

### 🧩 Bug拆解师（问题结构化）
- **职责**：一个 Bug 报告进来先拆解——症状/复现步骤/影响面/严重级/疑似根因假设清单，把模糊反馈（"窗口不对劲"）转成可定位的结构化工单，分派给定位师。复杂复合 Bug 拆成独立子 Bug，防止"一把梭改一堆引入新问题"。
- **产出**：Bug工单（含假设清单按优先级排序）。

### ✨ Bug优化师（防补丁腐化）
- **职责**：修复合入后回看——①补丁是否该收敛为通用机制（如逐个CSS→基类）；②是否引入技术债；③同类历史补丁是否可以合并清理。定期（或每5次修复）出一份"补丁健康报告"。
- **产出**：优化建议清单（采纳/挂账）。

## 三、协作流水线（闭环）

```
用户报Bug / 巡检发现异常
        │
   [Bug拆解师] ── 结构化工单（症状/复现/假设清单）
        │
   [Bug定位师] ── 铁律三步（栈→二分→复核），钉死根因+证据
        │
   [Bug修复师] ── 按根因最小修复 + 运行时实测生效（HTTP/md5，非静态确认）
        │
   [Bug排查师] ── ①全局扫雷同类隐患 ②复发比对 ③写免疫卡
        │
   [Bug优化师] ── 补丁收敛/技术债回看
        │
   [验证师/审核员] ── 既有终验关口（复用，不重复建设）
```

- 小 Bug 可跳级：症状明确时拆解师可省，定位+修复合并；但**排查师的免疫卡不可省**——它是防复发的关键一环。
- 五师是"角色库新角色 + 提示词编排"，不需要新代码：与现有验证师/反驳师/审核员同机制（private/roles_db.json 追加角色条目，附专属 prompt）。

---

## 四、免疫卡格式（防复发核心资产）

```md
# 免疫卡-<编号> <一句话规则>
【症状特征】看到什么现象要想到这个坑
【根因】一句话因果链
【第一步检查】开工/排查时的第一个动作（可执行）
【历史案例】project_record 对应记录名 + commit
【适用范围】前端/后端/某文件/某机制
```

配套注入规则：全局工作纪律追加一条——**修 Bug 前先 `project_record search` 免疫卡分区，命中即按卡执行第一步检查，绕卡上手视为违规**。

---

## 五、落地方式（最小改动）

1. **写角色**：private/roles_db.json 追加 5 个角色条目（id: r_bug_fixer / r_bug_locator / r_bug_hunter / r_bug_splitter / r_bug_optimizer，头像 🐛🎯🔍🧩✨），prompt 按上文职责+红线写。
2. **加纪律**：public/prompts/模式2_工具循环/00_全局工作纪律.txt 追加"免疫卡检索"一条。
3. **建分区**：project_record 约定「定位/」「免疫卡/」两个分区名。
4. 不改任何 server 代码，纯提示词层落地，零风险可回滚。

## 六、验收标准
- roles_db.json 有 5 个新角色且 prompt 含各自红线
- 工作纪律含免疫卡检索条款
- 用一个历史真实 Bug（如"改了server/public不生效"）走一遍流水线演练，五师产出齐全
