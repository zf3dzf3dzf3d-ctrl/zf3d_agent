【全局工作纪律（最高优先级，所有工作对话必须遵守）】

一、Git 快照纪律（对话级隔离）
1. 对话开始时的第一件事：运行 `git status`。若工作区有未提交改动，先用 `git log --oneline -3` 和 `git diff` 判断是否上一对话遗留：
   - 是遗留且无害 → 提交为 `[carryover] ...` 后再开工；
   - 不确定 → 向用户说明，不要在脏工作区上直接做快照对比。
2. 绝不在脏工作区上把工作区改动当作"本对话的改动"来归因或回滚。
3. 任务结束时必须提交：`git add <本任务改动的逐个文件路径> && git commit -m "任务名: 改了什么/为什么"`（message 必须有语义，不许只写 checkpoint；禁止用 `git add -A` 一把扫，详见第 8 条）。
4. 临时调试文件（debug_*.py、临时截图、测试数据等）收尾时要么删除，要么加入 .gitignore，不许留在工作区。
5. server/logs/ 等运行时数据已在 .gitignore 中，不要重新 git add。
6. 验收标准：HEAD 与本对话开始点的 diff = 本对话真实改动。
7. 【自动快照抢入库·条件触发归因】本系统存在"会话开始自动快照"机制，会把工作区改动提前收录进快照 commit，导致行级归属与人工 commit 不符。为避免每对话都做昂贵归因，仅在满足任一条件时才强制 blame：① 快照 diff 出现异常（多了没做过的改动/少了不该动的文件）；② 本任务动过 server/ 等核心代码；③ diff 与完成消息声称不符。触发时用 `git blame -L <起>,<止> <文件>` 对**首个可疑文件的关键行**实查，定位到真实入库 commit 即停（不必逐文件全量 blame）；未触发则只做双快照对比，不强制 blame。
8. 【精确暂存·默认禁用 git add -A 收尾】人工收尾提交默认用 `git add <本任务逐个文件路径>` 精确暂存，禁止无差别 `git add -A`（会把并行会话遗留文件扫进本任务 commit）。白名单放行：纯提示词/记录类改动允许整目录一次添加 `git add -A -- public/prompts/ private/记忆/`。若开工时工作区已有遗留未提交改动，先单独提交为 `[carryover] ...` 或保持不动，绝不为省事无差别一把扫。

二、改动原则
1. 修改前先读懂现有代码，改动最小化，不做无关重构。
2. 修改 .py/.js/.css 后如服务器支持热更新则无需重启，但改动涉及 server 启动逻辑时必须提示用户重启验证。
3. 每次修改文件前系统会自动备份 .bak，不要手动批量删除这些备份。

三、收尾（强制自验项）
1. 使用 task_complete 结束任务前，自查 git 快照 diff 与声称的改动一致。
2. 【blame 条件触发】满足第 7 条任一触发条件（异常 diff / 动过 server/ 核心代码 / 与声称不符）时，收尾前必须对声称改动做 blame 行级实查（抽样即可：首个可疑文件关键行，定位即停）；若真实入库 commit 是自动快照而非本次人工 commit，必须在完成消息中如实写明。未触发条件时只做双快照对比，不强制 blame。此项为 task_complete 前的硬性自验。
3. 若发现 diff 中有本对话之外的文件变动，在完成消息中明确指出，不冒领也不回滚。
