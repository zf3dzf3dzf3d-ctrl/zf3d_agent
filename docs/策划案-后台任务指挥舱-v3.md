# 后台任务监控面板重设计策划案 v3.0

> 目标：解决"看不到无头智能体在干什么"，同时全面美化界面。
> 2026-11-02 · 基于源码实查（mixin_jobs.py / db.py / app-jobs.js / app-jobs.css）

---

## 一、问题诊断（为什么要重做）

### 1.1 根因：数据链路只有"里程碑的两端"，中间是黑的

实查 `server/routes/mixin_jobs.py` 的 worker 代码，jobs 表的状态更新只有 5 处：

| 时机 | 更新内容 |
|---|---|
| 提交 | status=queued |
| worker 开始 | status=running |
| 流水线跑完/异常 | status=done / await_review / failed + report_json 摘要 |
| 续跑 | status=queued |

**结论：从 running 到 done 之间可能长达几分钟到几十分钟，期间 jobs 表一个字节都不更新。** 用户点开面板只能看到"running"三个字，完全不知道智能体现在在策划、施工还是审核阶段、在调什么工具、卡没卡。这正是 2026-10-23 那次"后台任务卡死"调查的实证结论（实际是慢，但面板无心跳 → 用户体感=僵死）。

具体缺口：
1. **无进度心跳**：worker 跑起来后 updated_at 不刷新，没有 elapsed 实时计时，没有"当前阶段"字段。
2. **无阶段细分**：swarm_pipeline 有策划/施工/审核多阶段，但 report 只在结束时落 `stages_done`，运行中看不到"正在第几阶段"。
3. **无工具级事件流**：agent_loop 的 on_event（tool_call/tool_result 里程碑事件，已确认是 dict 型非 token 级，见 CLI 策划案 v2 实证）在 Jobs 模式下直接被丢弃，只有 transcript 终局回看，运行中不可见。
4. **transcript 是"事后"的**：`/api/jobs/<id>/transcript` 按 session_id 拼 agent_turns，运行中轮询它只能看到已完成轮次，且无阶段标注、无工具时间线。

### 1.2 界面问题（现状 app-jobs.css / app-jobs.js）

1. 右侧抽屉式悬浮窗，信息密度低：列表只显示 goal + 状态色点，一眼扫不出"谁在跑、跑多久了"。
2. 状态只有 5 色（灰蓝绿橙红），无动画区分"活跃 vs 僵着"。
3. 详情/对话流是纯文本堆叠，无阶段进度条、无工具调用时间线。
4. 无失败重试的参数对比视图、无 token/耗时统计。

## 二、新设计方案

### 2.1 数据链路改造（治本：让"黑盒"变"直播"）

**核心思路：心跳 + 事件总线，零改内核主逻辑。**

#### A. Job 心跳与阶段上报（P0，改动最小）
- 在 `mixin_jobs.py` 的 `_pipeline_logger` 处拦截：内核的 log 消息本来就带阶段信息（`[job:tag] ...`），把每条 log 同时追加写 jobs 表新列 `log_tail TEXT`（只保留最近 20 条，JSON 数组）+ 刷新 `updated_at`。
- jobs 表加列：`stage TEXT`（planning/building/reviewing/summarizing）、`heartbeat_at REAL`。
- 前端列表即可显示"⏳ 审核阶段 · 已运行 6分32秒"，且心跳超过 120s 未更新 → 状态点变黄色呼吸灯（疑似卡住）。

#### B. 事件流接口（P1）
- worker 里把 on_event 钩子接到一个内存环形缓冲（每 job 最近 200 条 tool_event）。
- 新接口 `GET /api/jobs/<id>/events?after=<seq>` 增量拉取（SSE 或轮询均可，先轮询 3s）。
- 事件含：工具名、ok/fail、耗时、阶段、轮次。前端渲染成**工具时间线**：
  ```
  14:32:10 📖 read_file server/db.py           ✓ 0.3s   [施工]
  14:32:15 ✏️ replace_text server/routes/...    ✓ 1.1s   [施工]
  14:35:02 🔍 search_in_files "update_job"      ✓ 2.8s   [审核]
  ```
- 落库：事件同时 append 到 agent_turns 或独立 `job_events` 表，重启后仍可回看全程。

#### C. 阶段进度条（P0）
- 前端 4 段进度条：策划 → 施工 → 审核 → 总结。stage 字段点亮当前段，完成段打勾，失败段标红。
- 配合 report_json 的 stages_done 回填历史任务。

### 2.2 界面重设计

#### 布局：从"侧边抽屉"升级为"指挥舱"双栏布局
```
┌────────────────────────────────────────────────────────┐
│ ⠿ 后台任务指挥舱        [运行中 3] [总 12]   ─ □ ✕    │
├──────────────┬─────────────────────────────────────────┤
│ 任务列表(左栏) │           详情区(右主栏)                │
│ ▸ 🔍 搜索    │  ┌ 任务头：goal 全文 + 状态徽章 + 计时 ┐ │
│ ┌──────────┐ │  ├ 阶段进度条 ●─●─◐─○                │ │
│ │🟢 修复登录│ │  ├ Tab: 时间线 | 对话流 | 报告 | 配置  │ │
│ │ 6分32s   │ │  │                                    │ │
│ │ 审核◐    │ │  │  工具时间线（2.1B 的渲染）           │ │
│ ├──────────┤ │  │  支持按阶段/工具/成功失败筛选         │ │
│ │🔵 重构面板│ │  └────────────────────────────────────┘ │
│ │ 2分01s   │ │  底部操作条：⏸暂停(排队时) ↻重跑         │
│ │ 施工●    │ │             ✍️裁决(await_review 时)      │
│ └──────────┘ │                                          │
│ [+ 新建任务]  │                                          │
└──────────────┴─────────────────────────────────────────┘
```
- 保留悬浮窗形态（可拖拽/缩放，沿用现有 _bindDrag），但默认宽度加大到 900px。
- 左栏列表卡片：状态灯（含呼吸动画）+ goal 截断 + 阶段徽章 + 实时计时（前端每秒本地递增，不从服务器刷）。
- 状态灯动画规范：
  - 蓝=运行（脉冲）、绿=完成、橙=待审核（闪烁）、红=失败、灰=排队、**黄呼吸=心跳超时疑似僵死**（新增）。

#### 美化要点（视觉）
1. 深色玻璃拟态卡片（与工作台主风格一致），圆角 12px，卡片悬浮阴影。
2. 状态灯用 CSS box-shadow 光晕动画，不再是死板的色点。
3. 阶段进度条用渐变连接线，当前阶段有流动光效。
4. 时间线用左侧竖线+节点圆点的 timeline 样式，工具图标区分类型（读/写/搜/运行/浏览）。
5. 空状态插画：无任务时显示"没有任何后台任务，点 + 新建发活"引导。
6. 计时器数字用等宽字体 tabular-nums，避免跳动。

### 2.3 附加能力

| 能力 | 说明 | 优先级 |
|---|---|---|
| 心跳超时警示 | heartbeat 超 120s 前端标黄 + 一键"终止"按钮（kill worker 线程标志位） | P1 |
| 耗时/token 统计 | 卡片显示 elapsed；详情页显示 token 消耗（从 token_usage 表按 session 关联） | P2 |
| 多任务并发可视化 | 列表顶部显示当前并发 x/4（对应 _JOBS_SEM） | P2 |
| 声音/通知 | 任务完成/失败/待审核时 toast + 可选提示音 | P2 |
| 无头 CLI 任务接入 | cli.py --task-file 批跑的任务也注册进 jobs 表（source=cli 字段），面板统一看 | P2 |

## 三、实施步骤（建议 4 批，每批可独立验收）

1. **批次1（P0 数据链路）**：db.py 加列（stage/heartbeat_at/log_tail）+ mixin_jobs.py logger 拦截写心跳。验收：跑一个 job，3s 轮询能看到 stage 和 updated_at 持续刷新。
2. **批次2（P0 前端列表改版）**：app-jobs.js/css 列表卡片 + 阶段进度条 + 实时计时 + 呼吸状态灯。验收：浏览器实开面板截图核对。
3. **批次3（P1 事件流）**：on_event 接环形缓冲 + /events 增量接口 + 时间线 Tab 渲染。验收：运行中任务能实时看到工具调用行。
4. **批次4（P1/P2 打磨）**：心跳超时警示+终止、统计、通知、CLI 任务接入。

## 四、风险与约束

- 零改 swarm_pipeline 内核主逻辑（沿用 v2 设计原则），只在外壳拦截 log/on_event。
- on_event 已实证是里程碑级（非 token 级），事件量可控（每任务几十条），环形缓冲防内存膨胀。
- 写 jobs 表频率提高（每条 log 一次 UPDATE），SQLite 单写锁——用内存节流：同一秒内多次 log 合并成一次 UPDATE。
- 热更新：mixin_jobs.py 已在热重载注册表，前端 F5 即可，无重启负担。

## 五、验收总标准

用户提交一个后台任务后，打开面板 10 秒内能看到：当前阶段、已运行时长、正在调用的工具名；不需要任何猜测就知道"它活着且在干活"。
