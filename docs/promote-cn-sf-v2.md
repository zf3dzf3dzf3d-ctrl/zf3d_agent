## 正文

前段时间开源了自己的 AI 智能体工作台（MIT 协议），今天分享下它的技术实现思路，欢迎拍砖。

先说结果：服务端没有一行第三方依赖——没有 Flask、没有 FastAPI、没有 Node、没有 Docker，Python 3.11 标准库直接跑，解压双击启动。

### 一、为什么不用框架？

市面上 Agent 框架已经很多（LangChain、AutoGen……），但我想解决的是另一个问题：**给普通用户一个开箱即用的本地工作台**。这意味着：

- 安装门槛必须趋近于零：pip install 都不想要，因为"装环境"这一步就能劝退一半目标用户
- 数据必须全本地：对话记录、API Key、数据库都在用户自己电脑上
- 能在 Windows 上一键启动（目标用户很多不是程序员）

于是干脆死磕标准库。HTTP 服务器用 `http.server` + 多线程手写，路由自己分发，SQLite 标准库自带，任务调度自己写——该有的其实标准库都有。

### 二、架构分层

| 层 | 实现 |
|---|---|
| HTTP | `http.server` 多线程 + 手写 keep-alive |
| 路由 | 前缀匹配分发，GET/POST/DELETE 独立 dispatch |
| 存储 | 本地 SQLite + kv_store |
| 前端 | 原生 JS 模块化，无打包器，无限画布 Canvas 渲染 |
| Agent 内核 | 工具调用循环 + 自检 + 计划持久化 |

### 三、几个踩过的坑

**1. HTTP keep-alive 的请求体残留**

最诡异的一个 bug：控制台偶发 `501 Unsupported method ('{}GET')`。排查了半天，根因是 keep-alive 连接上，某些 handler 读完请求头就返回响应，没读请求体——残留的 `{}` 字节被下一个请求当成了请求行来解析。

修复思路：在 dispatch 入口统一按 Content-Length 排干请求体（drain），chunked 排不动的直接断连。所有 handler 共享这个入口，一次根治。

**2. Agent 的自我修复**

智能体执行出错直接把错误抛给用户，体验很差。所以在内核里加了自检循环：出错后自动重新读相关代码、定位根因、打补丁、再验证，而不是终止。

**3. 跨对话的任务连续性**

长任务往往跨很多轮对话。解决方案是把任务计划持久化为 Markdown 文件，新对话开场先读计划，找到断点接着执行——相当于给 Agent 一个"外置记忆"。

### 四、多智能体并发

每个对话是一个独立智能体，有独立的模型配置、工具集和上下文，实测可同时挂 400+ 个对话。智能体之间可以互相派活、汇总结果。可视化层面做了一个无限画布：节点即智能体，连线即依赖，本质上是个每个节点都会自己干活的 DAG 工作流引擎。

### 五、适不适合你？

适合：想在本地折腾 AI 工作流、对数据隐私敏感、或者单纯想看"零依赖架构怎么写"的同学。

不适合：需要多人协作/云端部署的场景（当前定位就是单机本地）。
