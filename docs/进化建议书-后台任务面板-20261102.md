# 进化建议书 · 后台任务面板策划（2026-11-02）

## 建议1【P0·必须先裁决基线】UI 方案落地前先解决"5.7.0 与 5.8.0 双版本分叉"
- 对象：项目版本管理流程 / docs/策划案-后台任务指挥舱-v3.md 批次2
- 改什么：策划案批次2（前端改版）默认在 5.8.0 现状上重做 UI，但实查本仓库 app-jobs.js 仅有基线提交 29f944f——10-31 在 5.7.0 完成并验证过的"单栏内联展开"改版（commit 339739a9 + 3184b778，+23/-8，已实测下发验证）**未同步到 5.8.0**。若直接按策划案从旧双栏重画，等于丢弃一次已验证的中间成果；若不裁决，两版本面板形态将持续分叉。
- 为什么：多版本并行（5.7.0 / 5.8.0 目录并存）且无共享分支，同一功能修两遍是可复现的模式（工作记忆中工作台页签修复、风筝穿透修复均在 5.7.0 提交）。
- 预期收益：避免重复施工与两版本行为不一致；UI 批次可直接以"内联展开"为起点叠加指挥舱设计。
- 落地方式：施工前由审核/用户二选一：A. cherry-pick 或手工移植 339739a9 到 5.8.0 再叠加 v3 设计；B. 明确放弃 5.7.0 改动按 v3 全新实现。建议在 v3 策划案批次2 补一行基线说明。

## 建议2【P1·方案加固】心跳写库方案补"锁审计门禁"再施工
- 对象：策划案 §2.1-A（logger 拦截写 jobs 表 + 同秒节流）
- 改什么：施工单须先 grep _pipeline_logger 全部调用点与 SQLite 连接的 check_same_thread/锁配置，确认 worker 线程与提交线程是否共用同一连接；节流合并逻辑本身含共享状态（timer/dirty 标记），须防"合并线程与最终 update 竞态丢最后一次状态"。
- 为什么：项目已有锁重入自死锁前科（对话池死锁事件复盘：栈中完全静默）；本次改动恰好在多线程 worker 里新增共享写路径，且异常时可能绕过节流 flush 导致 heartbeat 停摆被前端误判"卡死"——与本次要解决的问题同形。
- 预期收益：避免心跳机制自身成为新的"看起来卡死"来源；符合五·4 锁改动审计门禁。
- 落地方式：施工单加两行硬性要求：①调用方持锁审计表；②异常路径 finally 必 flush 心跳，测试用例含"异常中断后前端显示 failed 而非黄灯悬挂"。
